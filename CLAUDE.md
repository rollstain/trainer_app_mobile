# Порядок работы в репозитории

Правила для любого, кто вносит правки, — человека или ассистента. Устройство проекта и сборка —
в `README.md`.

## Ветка на задачу

Прямых коммитов в `main` нет. Любая задача начинается с ветки от свежего `main`:

```bash
git fetch origin
git checkout -b feature/working-hours-screen origin/main
```

Имя ветки — `<тип>/<суть>`: латиница, kebab-case, два-четыре слова о сути, а не о файлах.

| Тип | Когда |
|---|---|
| `feature/` | новая функциональность |
| `fix/` | исправление дефекта |
| `refactor/` | правка без изменения поведения |
| `chore/` | сборка, CI, зависимости, инфраструктура |
| `docs/` | только документация |

`feature/schedule-week-swipe`, `fix/token-refresh-race`, `chore/release-pipeline` — годятся.
`feature/new`, `fix/bug`, `patch-1` — нет.

## Коммит

Одна строка по-русски, повелительного наклонения избегаем — описываем сделанное:
«Листание недель в расписании: пара шевронов у тренера и клиента». Без служебных трейлеров,
без ссылок на сессии и без «Generated with». Тело коммита — только если одной строки мало
на объяснение «почему».

Список сообщений коммитов уходит в описание релиза, поэтому сообщение пишется для человека,
который его прочитает в Telegram, а не для истории файлов.

## Завершение работы

Когда задача сделана и проверена:

```bash
git push -u origin <ветка>
gh pr create --fill --base main
```

Описание PR заполняется по шаблону `.github/pull_request_template.md`. Дальше ветка ждёт ревью —
сливает её владелец репозитория, автор PR не мержит сам.

CI на PR обязан быть зелёным: detekt, юнит-тесты, debug APK, линковка iOS-фреймворка.

## Релиз

Команда «отведи релиз» означает следующее:

1. `main` зелёный, всё нужное слито.
2. Версия по semver: правки без новых экранов — patch, новая функциональность — minor.
3. Тег на `main` и пуш тега:

```bash
git tag -a v0.2.0 -m "Расписание неделями, рабочие часы тренера"
git push origin v0.2.0
```

Дальше `release.yml` сам: собирает подписанный APK, считает изменения от прошлого тега и шлёт
файл в Telegram, а на GitHub создаёт Release с тем же текстом.

Отладочная сборка на любой ветке — кнопка **Run workflow** у `release.yml` в Actions, тип сборки
`debug`. Тег при этом не нужен и не создаётся.

## Что в репозиторий не попадает

- `*.jks`, `*.keystore`, `keystore.properties` — ключи подписи;
- `local.properties` и всё, что указывает на локальные пути;
- APK и AAB — их место в артефактах Actions и в Telegram.

Секреты живут в GitHub Secrets репозитория, список — в `docs/release.md`.

## Правила кода

- Комментариев в коде нет. Нужен комментарий — плохо названа функция или переменная.
- `!!` запрещён: `checkNotNull` с сообщением или ветвление.
- Числовые литералы — в `private const val` с именем, объясняющим значение целиком.
- Строки — только в `core_strings` и `uikit`, иначе ресурс не попадёт в APK.
- Новая таблица SQLDelight требует миграции `.sqm`, иначе старые установки падают.
- Цвета и отступы — токенами `uikit`, не литералами.
