# Бриф на дизайн-систему для Claude Design

Скопировать целиком как промпт. Документ самодостаточен: код читать не нужно.

---

## Задача

Спроектировать дизайн-систему на токенах и компонентах для мобильного приложения «тренер ↔ подопечные».
**Две темы обязательны: светлая и тёмная.** Платформы — Android и iOS, один общий UI на Compose
Multiplatform, то есть одна визуальная система на обе платформы без раздвоения.

Нужны, в порядке важности:

1. **Токены** — цвет, типографика, отступы, радиусы, размеры, состояния.
2. **Компоненты** с явными вариантами и состояниями.
3. **Экраны**, собранные из этих компонентов (список ниже, восемь штук).

---

## Что за продукт

Персональный тренер ведёт своих подопечных в одном приложении вместо переписки в четырёх
мессенджерах. Внутри:

- **чат** тренера с каждым подопечным;
- **календарь тренировок** — тренер ставит слоты, клиент записывается и просит перенести;
- **дневник тренировок** — клиент записывает упражнения, подходы, вес, время; тренер это читает
  и анализирует (образец жанра — GymKeeper);
- **карточка подопечного** с пометками тренера, в том числе медицинскими: «протрузия L4-L5», «грыжа».

**Пилот — несколько знакомых тренеров и их клиенты.** Не масс-маркет: интерфейс должен быть
рабочим инструментом, а не витриной.

### Две роли — два разных интерфейса

Это главная особенность. Одни и те же сущности выглядят по-разному:

| | Тренер | Клиент |
|---|---|---|
| Чат | Список диалогов со всеми подопечными, как в Telegram | Один диалог со своим тренером |
| Календарь | Своя неделя целиком: кто на какой слот записан, входящие заявки | Календарь тренера: только «свободно / занято / это моя тренировка» |
| Дневник | Читает дневники подопечных за период | Ведёт свой, вводит подходы |
| Карточка | Пишет пометки о подопечном | Не видит их вовсе |

**Приватность зашита в продукт:** клиент никогда не видит, кто записан на соседний слот — только
что время занято. В макетах клиентского календаря не должно быть ни имён, ни аватаров чужих людей.

Интерфейс русскоязычный. Кириллица, длинные слова («Перенести тренировку», «Подтвердить заявку») —
типографика и кнопки должны это переживать без обрезаний.

## Экраны

Ровно восемь, все уже существуют в коде как состояния — состав данных менять нельзя, можно менять подачу.

1. **Вход по приглашению.** Тренер присылает ссылку или короткий код из 6 символов (буквы и цифры,
   без похожих символов). Экран: поле кода, имя, кнопка. Максимально короткий путь — это единственный
   барьер между человеком и приложением.
2. **Список диалогов** (тренер). Строка: имя собеседника, превью последнего сообщения, время,
   счётчик непрочитанных. Сортировка по времени последнего сообщения.
3. **Диалог.** Свои и чужие сообщения, вложения (фото, видео, PDF), поле ввода, прикреплённые
   файлы до отправки, подгрузка старых сообщений вверх.
4. **Календарь тренера.** Неделя, переключение недель, слоты по дням: время, длительность, статус,
   имя записанного клиента. Отдельно — входящие заявки на перенос и отмену.
5. **Календарь глазами клиента.** Выбор тренера (их может быть несколько), неделя, слоты:
   свободен / занят / моя тренировка. Действия: записаться, попросить перенос, попросить отмену.
6. **Карточка подопечного.** Список пометок и редактор пометки.
7. **Дневник: ввод за день** (клиент). Выбор упражнения, строки подходов, заметка к дню.
8. **Дневник: просмотр за период** (тренер). Дни, внутри — подходы и суммарный объём за день.

## Состояния, которые обязаны быть в компонентах

Это не пожелания — ровно эти значения приходят из бизнес-логики, и для каждого нужен свой вид.

**Доставка сообщения:** `PENDING` (лежит в очереди, сети нет) · `SENT` · `FAILED` (не ушло).
Приложение работает офлайн: неотправленное сообщение видно сразу и должно отличаться от
отправленного однозначно, без вглядывания.

**Слот тренировки:** `FREE` · `BOOKED` · `CANCELLED` · `COMPLETED`. Плюс независимый признак
«по слоту висит заявка на изменение» — он накладывается на любой из статусов.

**Заявка на изменение:** вид `RESCHEDULE` / `CANCEL`, статус `PENDING` / `APPROVED` / `REJECTED`.

**Пометка о подопечном:** `MEDICAL` / `GENERAL`, плюс «закреплена». Медицинские сортируются выше
и должны читаться с одного взгляда: это ограничения по здоровью, из-за которых тренер меняет
программу. Спрятать их в серый мелкий текст — прямой вред.

**Упражнение:** `STRENGTH` (повторы + вес) · `BODYWEIGHT` (повторы) · `CARDIO` (время или дистанция).
От типа зависит, какие поля показывать в строке подхода — это три разных набора полей, а не один
с прочерками.

**Общие состояния каждого экрана:** загрузка (шиммер), пусто, ошибка с кнопкой «Повторить».
Нужен единый шаблон для всех трёх, а не три разных решения на разных экранах.

## Требования к самой системе

Это условия реализации — их нарушение делает макет невыполнимым.

### Токены

- Цвета **только семантические**: не «серый-500», а «фон экрана», «фон поверхности», «текст основной»,
  «текст второстепенный», «акцент», «опасность», «успех», «граница». Каждый токен обязан иметь пару
  «светлая / тёмная».
- Отступы и размеры — фиксированная шкала (4, 8, 12, 16, 20, 24, 32…). Произвольных значений быть
  не должно: в коде отступ берётся из токена, литералов вроде `13.dp` не будет.
- Тёмная тема — **не инверсия светлой**. Отдельно продуманные фоны поверхностей и границы.

### Компоненты

- **Варианты — перечисления, а не набор булевых флагов.** Не «isLarge + isDanger», а свойство
  «размер» со значениями и свойство «тон» со значениями. Комбинации флагов порождают состояния,
  которых в системе нет.
- **Необязательный элемент — отдельный вариант, а не «пустое место».** Если у строки может не быть
  подписи или иконки, это варианты «с подписью» и «без подписи», а не полупрозрачная заглушка.
- **Общие свойства — плоско, специфичные — внутри варианта.** У компонента есть общие поля
  (заголовок, действие) и поля, зависящие от варианта; их не надо смешивать в один плоский список.
- **Снять все размеры сразу.** Для каждого компонента и каждого его варианта нужны высоты, паддинги,
  промежутки, размеры иконок. Точечная доработка по одному замечанию за итерацию — самое дорогое,
  что может случиться дальше.
- Не создавать компонент под один экран. Если что-то нужно дважды — это компонент системы; если
  один раз — это композиция существующих.

### Ожидаемый состав библиотеки

Минимум: кнопки (основная, второстепенная, текстовая, опасная), поля ввода (текст, многострочное,
числовое), ячейка списка, аватар с инициалами, бейдж-счётчик, чип-статус, верхняя панель, нижняя
навигация, диалог подтверждения, шит снизу, тост, состояние-заглушка (пусто / ошибка / нет доступа),
шиммер-плейсхолдер, пузырь сообщения, поле ввода сообщения с вложениями, карточка слота, карточка
пометки, строка подхода в дневнике.

---

## Чего в системе быть не должно

- **Платных разделов, подписок, витрин покупки** — монетизация отложена, макетов не нужно.
- **Раздела фармакологии** — исключён сознательно.
- **Веб-версии** — только мобильные экраны.
- **Аватаров-фотографий** — в продукте их нет, только инициалы.
- Иллюстраций и маскотов: инструмент для работы, не развлечение.

---

## Что вернуть

1. Полные таблицы токенов — обе темы рядом, значения явные.
2. Компоненты со всеми вариантами и состояниями, с проставленными размерами.
3. Восемь экранов, собранных из компонентов, — в обеих темах.
4. Отдельно: как выглядят три служебных состояния (загрузка, пусто, ошибка) на примере одного экрана.
