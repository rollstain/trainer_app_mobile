## Пагинация списков (2026-08-28)

Контракт выбран так, чтобы **старое приложение не сломалось**: без параметра `limit` эндпоинт
отдаёт весь список, как раньше; при `limit` — страницу, а курсор следующей уезжает в заголовок
`X-Next-Cursor`. Тело ответа остаётся массивом, поэтому клиент, который про пагинацию не знает,
ничего не замечает. Курсор keyset-овый (`имя|id` в base64), а не offset: вставка нового элемента
не сдвигает страницы.

- [x] 43. `GET /exercises?limit=2` — три полные страницы, 0 дубликатов, набор совпал с полным списком ✅
- [x] 44. Пустой страницы в конце нет: сервер берёт `limit + 1` строку и по ней понимает, есть ли ещё ✅
- [x] 45. Без `limit` — весь список и никакого заголовка (обратная совместимость) ✅
- [x] 46. `GET /coach/clients?limit=1` работает, порядок стал детерминированным (по имени, затем id) ✅
- [x] 47. Справочник в приложении грузится страницами по 30 и подгружает следующую по достижении конца ✅
- [x] 48. На коротком списке «хвост» подгрузки не появляется (проверено на эмуляторе, 3 упражнения) ✅

Заодно в `GET /coach/clients` убран N+1: пользователи забираются одним `findAllById`, а не по одному
на каждого подопечного. Порядок раньше был не определён (какой отдаст БД) — теперь по имени.

**Пагинацию «Людей» в UI сознательно не включал.** Экран сортирует список на клиенте
(сначала записанные на тренировку, потом по алфавиту), а сервер отдаёт страницы по алфавиту —
подгруженные люди прыгали бы в середину списка. Серверная часть готова; когда список вырастет,
правильный ход — разделить экран на «Записаны» (грузится целиком, их мало) и «Остальные»
(страницами), либо перенести признак ближайшей тренировки на сервер.

Осталось в прод-базе: 6 тестовых упражнений у **тестового** тренера (эндпоинта удаления нет).
У Ляшука в справочнике их не видно — выдача фильтруется по coach_id.

подопечные», и брать это из агрегата нельзя — агрегат грузится best-effort, и при его сбое экран
показал бы «подопечных нет» вместо блоков. Один запрос против риска соврать.
